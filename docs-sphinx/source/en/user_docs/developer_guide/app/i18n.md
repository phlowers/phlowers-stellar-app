# Internationalization (i18n) — Transloco

Stellar uses [Transloco](https://jsverse.github.io/transloco/) for all user-facing text. Angular's
native i18n (`$localize`, `.xlf`, `i18n` attributes, `ng extract-i18n`) is not used anywhere in
this codebase.

## Summary

**Run locally:** nothing special to configure — `public/assets/config/app-config.json` is committed
with `defaultLang: "fr"` and is served as-is by `npm run start` / `ng serve`. Switch language at
runtime from the UI language selector, or edit that file manually to change the default.

**Run in Docker:** the default language is a build-time argument, embedded in the image; changing it
requires rebuilding:

```bash
docker build --build-arg DEFAULT_LANGUAGE=en ...
```

See [Build-time configurable default language](#build-time-configurable-default-language-assets-config-app-config-json)
below.

**Adding a new translated string** (workflow):
1. Search `public/i18n/en.json` for an existing key under `common.*` before adding a new one —
   never duplicate.
2. Add the key to both `public/i18n/en.json` and `public/i18n/fr.json`, nested by
   feature/component instead of using a flat dot-joined key. Follow the namespace and naming rules
   in `.github/instructions/i18n.instructions.md` (for example `<feature>.<component>.*`,
   `common.*`, `routes.*`, `aria-*`, `placeholder-*`).
3. Use it in templates via `{{ 'key.path' | transloco }}` (or `transloco: { param }` for
   interpolated values), or via `TranslocoService.translate('key.path')` in TypeScript when the
   pipe is not usable (see [Known exception](#known-exception)).
4. There is no build-time extraction step and no lint rule forcing `en/fr` parity — a missing key
   simply renders as the raw key at runtime, so both files must be checked manually before
   committing.

**Other useful facts:**
- Translation JSON is fetched lazily and non-blocking at startup (see
  [Bootstrap wiring](#bootstrap-wiring-src-main-ts-src-app-app-config-ts)) — first render never waits
  for the network.
- Route `<title>` values are translation keys resolved by a custom `TitleStrategy` (see
  [Route titles](#route-titles-translocotitlestrategy)).
- `reRenderOnLangChange: true` is enabled in `main.ts`, so switching language at runtime re-renders
  the whole app without a page reload.

## Translation files

Two JSON files, one per language, nested by feature/component:

```
public/i18n/en.json
public/i18n/fr.json
```

The folder is named `i18n` rather than `assets/transloco` because this is Transloco's documented
convention (`TranslocoHttpLoader` fetches `i18n/{lang}.json` by default). It predates the app and
is kept as-is; it is unrelated to Angular's native i18n system. See `src/transloco-loader.ts` for
loader implementation and `.github/instructions/i18n.instructions.md` for naming conventions.

## Translation key naming convention (i18n)

A naming strategy has been established to avoid duplication and maintain consistency across the
project.

### Structure

Translation files (`public/i18n/en.json` and `public/i18n/fr.json`) use a **hierarchical nested
structure**, never a flat map:

```json
// ✅ Correct
{ "sections-tab": { "col-name": "Section Name" }, "common": { "save": "Save" } }

// ❌ Forbidden — never flatten the path into a single property
{ "sections-tab.col-name": "Section Name" }
```

### Namespaces

| Namespace | Usage | Examples |
|-----------|-------|----------|
| `common.*` | Generic text reused across features | `common.save`, `common.cancel`, `common.delete` |
| `routes.*` | Browser tab titles via `TranslocoTitleStrategy` | `routes.login`, `routes.study`, `routes.admin` |
| `shared.python-errors.*` | Python engine error messages | `shared.python-errors.solver-error` |
| `shared.<service-name>.*` | Text reused by multiple components or generated by a service | `shared.obstacle-form-service.save-detail` |
| `<feature>.<component>.*` | Text specific to one component | `sections-tab.col-name`, `manual-section.tab-general` |

### Key construction rules

- **Kebab-case** for each segment: `sections-tab.col-name` not `sectionsTab.colName`
- **Specificity**: `supports-table.aria-chain-name` not `supports-table.aria-1`
- **Aria labels**: prefix `aria-*` — `supports-table.aria-open-attachment-modal`
- **Placeholders**: prefix `placeholder-*` — `sections-tab.placeholder-view-ic`
- **Notifications**: namespace `<feature>.notifications.*`
- **Service errors**: `shared.<service-name>.*` — `shared.section-import.file-read-error`
- **Interpolated values**: syntax `{{ param }}` —
  `"studio.conformity.calculation-failed-error": "Calculation failed: {{ errorMessage }}"`

### Before creating a key

**Always search in `en.json` first** to see whether a key already exists. If it is under `common.*`,
reuse it instead of duplicating it.

## Bootstrap wiring (`src/main.ts` / `src/app/app.config.ts`)

- `provideTransloco()` is registered in `main.ts` with `availableLangs: ['en', 'fr']` and a
  fallback `defaultLang: 'fr'`.
- The actual active language is resolved at runtime by `AppConfigService.loadDefaultLang()` in the
  `APP_INITIALIZER` from `app.config.ts` and applied via `TranslocoService.setActiveLang()`.
- The translation JSON fetch (`TranslocoService.load()`) is intentionally fire-and-forget: it must
  not block first render, since `i18n/*.json` goes through the same OIDC-protected route as other
  assets and can stall during an OIDC renegotiation. Components read translations reactively through
  the `transloco` pipe.

## Build-time configurable default language (`assets/config/app-config.json`)

`AppConfigService` fetches `assets/config/app-config.json` (a plain
`{ "defaultLang": "en" | "fr" }` file) to decide which language to activate.

A default copy is committed at `public/assets/config/app-config.json` (`defaultLang: "fr"`), so it
works out of the box for local development.

In the Docker image, this file is regenerated at build time from the `DEFAULT_LANGUAGE` arg (default
`fr`, as defined in `Dockerfile`), overwriting the checked-in copy:

```bash
RUN mkdir -p /usr/share/nginx/html/assets/config && echo "{\"defaultLang\": \"${DEFAULT_LANGUAGE}\"}" \
    > /usr/share/nginx/html/assets/config/app-config.json
```

Changing the language for a Docker deployment therefore requires rebuilding the image with a different
`--build-arg DEFAULT_LANGUAGE=...` value — it is not a runtime-only override.

- `AppConfigService.loadDefaultLang()` falls back to `'fr'` with a warning if the file is missing,
  malformed, or the request times out after 3s (bounded intentionally: the `APP_INITIALIZER` must not
  block first render).

## Route titles (`TranslocoTitleStrategy`)

Transloco has no built-in integration with Angular Router's `TitleStrategy`. Route `title:` values are
interpreted as translation keys (namespace `routes.*`, for example `routes.login`) and resolved by a
custom `TranslocoTitleStrategy` (`src/app/core/strategies/transloco-title.strategy.ts`), registered in
`app.config.ts` via `{ provide: TitleStrategy, useClass: TranslocoTitleStrategy }`.

## Known exception

`manualSection.component.ts` calls `TranslocoService.translate(...)` imperatively instead of using the
`| transloco` pipe because PrimeNG `p-paginator` placeholders (`{first}`, `{last}`, `{totalRecords}`)
conflict with Transloco's interpolation syntax. See the `// TODO: STOP #2` comment in
`manualSection.component.html` and `.github/instructions/i18n.instructions.md`.
